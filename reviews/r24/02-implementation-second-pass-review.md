## New findings

### F1 — `KeyValueEditorControl` Remove button binding is broken

**Severity**: Medium
**File**: `ScraperTool/Controls/KeyValueEditorControl.xaml` line 29

The Remove button inside the `DataTemplate` binds to:

```xaml
Command="{Binding DataContext.RemoveCommand,
    RelativeSource={RelativeSource AncestorType=ItemsControl}}"
```

This resolves to `ItemsControl.DataContext.RemoveCommand`. The `ItemsControl` inherits
its `DataContext` from the parent ViewModel (`ProviderManualEditorViewModel`). The
ViewModel has `RemoveProtocolConfigEntryCommand` (generated by `[RelayCommand]`), **not**
`RemoveCommand`. The binding target does not exist, so the button is silently disabled
and the user cannot remove entries.

Compare with the Add button (line 37), which binds correctly:

```xaml
Command="{Binding AddCommand,
    RelativeSource={RelativeSource AncestorType=UserControl}}"
```

**Fix**: Change the Remove button binding to match the Add button pattern:

```xaml
Command="{Binding RemoveCommand,
    RelativeSource={RelativeSource AncestorType=UserControl}}"
```

The `CommandParameter="{Binding}"` already passes the item correctly.

### F2 — Five DI registration tests fail at runtime

**Severity**: Medium (pre-existing, carried from refactor 23)
**File**: `AIProviderConnectLib.Tests/DependencyInjection/AIProviderRegistrationBuilderTests.cs`

Five tests fail when the full test suite runs:

1. `Parameterless_AddAiProviders_StillRegistersEmbeddedProviders`
2. `NoOverrides_ResolvedProviderIsNotDecorated`
3. `AddAiProviders_CustomNewId_ResolvesProviderFromContainer`
4. `AddProvider_RegistersCustomProvider_AndExcludesIdFromProtocolLoop`
5. `OverrideModels_WrapsResolvedProvider_AndMergesCatalog`

All five call `provider.GetServices<IAIProvider>()` (non-keyed resolution), but providers
are registered only as keyed singletons via `AddKeyedSingleton<IAIProvider>(providerId, ...)`.

**Root cause**: Refactor 23 removed the non-keyed forwarding registration:

```csharp
// This line existed in commit 6f1779e but was removed in 53494cd:
services.AddSingleton(sp =>
    sp.GetRequiredKeyedService<IAIProvider>(providerId));
```

Without this forwarding, `GetServices<IAIProvider>()` returns an empty collection.
The tests were written when the forwarding existed and were not updated when it was removed.

**Impact**: Not caused by refactor 24, but the refactor 24 implementation was committed
on top of this broken state and the tests remain red.

### F3 — No `MessagesApiProvider` test class exists

**Severity**: Low
**File**: `AIProviderConnectLib.Tests/Providers/` (missing file)

The `Providers/` test folder contains test classes for `AIProviderBase`,
`HybridGatewayProvider`, `KeyQueryProvider`, `ModelCatalogProvider`, and
`ModelCatalogOverrideDecorator` — but no `MessagesApiProviderTests.cs`.

The `MessagesApiProvider` has unique behavior (auth-header resolution via
`CustomAuthHeaderName`, `InvalidOperationException` when the header name is missing)
that is not covered by any provider-level test. The existing
`MessagesApiProtocolTests` only test request/response mapping, not the provider itself.

### F4 — `gemini.json` carries `modelsEndpoint` despite `KeyQuery` having no configurable models endpoint

**Severity**: Low (subset of first-review Issue 2, more specific)
**File**: `ai-providers/gemini.json` line 19

`gemini.json` contains `"modelsEndpoint": "models"`. This field is deserialized onto
`ProviderDefinition.ModelsEndpoint` but never reaches runtime because `KeyQueryOptions`
has no `ModelsEndpoint` property and `SeedFromDefinition` does not seed it. The
`KeyQueryProvider.GetModelsAsync` hardcodes `EndpointDefaults.Models` (which happens to
be `"models"`). The JSON field suggests configurability that does not exist.
